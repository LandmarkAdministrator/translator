## 1. What broke during the morning service, and why

Three faults hit in sequence. All are fixed; the reasoning matters more than
the diffs.

### The hang watchdog killed the service repeatedly

`translate-window-check.sh` restarts translation when `~/translate.log` has
been silent for `STALL_SECONDS`. That was 180 s, sized for the legacy
`translate.py`, which logged continuously.

**The unified stack only logs when someone speaks.** The service window opens
at 09:15 for a 10:00 service, so the room is silent for 45 minutes. The
watchdog read that as a hang and restarted — and each restart takes ~40 s to
load models, which is also silent, so it kept killing what it was reviving.

```
09:15:43  in window, was not running -> started
09:20:06  in window, log stalled 180s -> restarted (hang watchdog)
09:45:43  in window, log stalled 180s -> restarted (hang watchdog)
```

Fix: `STALL_SECONDS` 180 → 900, plus a new `MIN_UPTIME=300` so a service still
loading models can never be restarted. Verified: the stack then ran **618 s of
silence with zero restarts**.

*This was the first Sunday on the unified stack, which is why it had never
appeared.*

### The service unit was switched to the legacy program mid-service

At 10:01 `ExecStart` was pointed at `~/bin/start-translate` (legacy). Room audio
kept working, but `translate.py` has no relay to the web server, so the
congregation page showed **"No service in progress" while audio played** — 12
people had it open.

Nothing automated does this; it was manual. But nothing guarded it either.

Fix: `ensure_program()` in the scheduler restores `ExecStart` every five minutes
and logs it. The admin panel's Start/Restart do the same before launching. See
§4.

### The GPU reached 90 °C with the thermal guard silent

The guard's entire trip body sat behind `if translate.service is active`. The
*archive backlog* was heating the card, so the guard did nothing — not even log
— while the RTX 3060 (OEM fan replaced with a case fan) hit 90 °C with
`sw_thermal_slowdown` already engaged.

Fix (`scripts/ops/gpu-thermal-guard.sh`): a trip now always stops the backlog
and logs, and resumes it automatically below 70 °C, but **only removes a stop it
placed itself** — the scheduler uses the same stop file to drain before a
service, and clearing that would start archive work mid-service. Stopping
`translate.service` still sets the manual override, because an interrupted
service needs a human.

Verified in production: trip at 85 °C within 5 s, automatic resume 70 s later,
peak down from 90 °C to 87 °C.

## 2. The flush policy — the largest quality change

### The problem

Sentences were cut mid-clause, so NLLB received fragments without subjects and
invented them:

```
EN  made a tradition of washing hands and were ready to beguile…
ES  El Parlamento Europeo ha hecho una tradición de lavarse las manos…
```

Worse, content was **silently dropped** — 10% of segments, every case a segment
containing two sentences.

### What was actually causing it

Measured over 10 minutes of sermon with production's 1.5 s chunks:

```
flush triggers today: hard_timeout 55, punctuation 15, silence 9
```

**The 6-second hard timeout was doing 69% of the segmenting** — chopping on a
timer regardless of content. The silence timeout, which was the obvious
suspect, fires 9 times in 10 minutes: during continuous preaching the ASR emits
text on 96% of chunks, so there are only 15 empty chunks for it to fire on.

### The fix

The ASR reports sentence ends by putting the mark at the **head of the next
fragment** (`[…through the sky]` then `[. The grain shall then be]`). That is a
boundary signal, and the old code deleted it. Now:

- a fragment opening with `.?!` closes the buffered sentence, keeping the mark
- a mark landing mid-fragment splits the buffer too (two sentences in one
  segment is what made NLLB drop one)
- `SENTENCE_MAX_WORDS=60` and `SENTENCE_HARD_TIMEOUT=15` are safety valves,
  firing ~3 times in ten minutes

### Results

10-minute sermon:

| | old | new |
|---|---|---|
| WER | 3.07% | **2.64%** |
| ends with `.?!` | 18.3% | **96.1%** |
| leads with a mark | 19.5% | **0%** |
| span median | 6.3 s | **4.8 s** |
| span p90 | 7.9 s | 13.7 s |

WER *improved* because flush boundaries no longer split subword joins
("pass age" → "passage"). The median got faster because a finished sentence is
released immediately instead of waiting for a timer. Only the p90 pays, and the
old 8 s ceiling was artificial — produced by cutting sentences in half.

Translation of the same audio (LaBSE, source vs translation):

| | Spanish | Creole | Russian |
|---|---|---|---|
| good (≥0.80) | 99.0% | 96.1% | 91.2% |
| poor (<0.65) | 0% | 0% | 0% |
| content dropped | 0 | 0 | 0 |

Against what congregants received that morning: Spanish good **61.2% → 99.0%**,
content dropped **10% → 0%**.

`suite_v4` (56.8 min, five tracks) — no regression anywhere:

```
track       ref w   OLD      NEW     OLD ends  NEW ends
jfk          1365   2.49%    2.64%      4.5%     46.8%
sermon       1857   2.75%    2.75%     18.7%     97.0%
jobs         2270   2.38%    2.11%      7.3%     95.3%
singing       359  45.40%   44.57%      0.0%     23.5%
libri-mix    1415   4.45%    3.96%      5.7%     70.5%
weighted     7266   5.02%    4.83%
```

JFK is the only track where WER rose (+0.15): long formal oratory supplies few
sentence marks so the word cap does more work. Preaching is not that register.
**The singing figure is pessimistic for this site** — the test recording has
instruments, the live mixer feed does not.

## 3. Russian (third language)

Requested by a congregant. Live in `config/site.json` (page) and
`config/settings.yaml` (pipeline).

- NLLB `rus_Cyrl`, 0.70 s/sentence; `facebook/mms-tts-rus`, RTF 0.070 on the 3060
- **Routed to the mini PC's onboard analog jack** (`ALC269VC Analog`), because
  the Behringer's two channels are taken by Spanish (left) and Creole (right).
  Its second channel is free for a fourth language.
- **Nothing is physically plugged into that jack yet** — the page carries
  Russian; the room does not.

**A language needs `<CODE>_TTS` set in `scripts/run_production.sh`.** Without
`RU_TTS=mms`, Russian fell through to Piper, which has no Russian voice, and the
failure is not graceful — it raises during pipeline load and the whole service
crash-loops, taking Spanish and Creole with it. Caught by a dry run four hours
before a service.

`PipelineConfig.web_only` exists for a deployment with no spare output. Nothing
uses it now.

**Open:** the ten short-phrase Russian entries in `translate_short_dict.py`
(`Аминь.`, `Спасибо.`…) were written by me and have not been reviewed by a
Russian speaker. That dictionary intercepts very short utterances before NLLB,
which hallucinates on them (`Amen.` once became *"- No lo sé."*). Spanish and
Creole entries were validated by the sister project's voter panel; Russian
was not.

## 4. Legacy program retired

The unified stack wins on every measure (2.4% vs 3.3% WER, ~8 s vs ~46 s
latency, and it feeds the page at all), so maintaining both stopped being worth
it.

- `~/bin/start-translate`, `start-translate-legacy`, `translate.py`,
  `translate-catchup.py`, `translate-t5.py` → `~/legacy-retired-20260906/`
  with a README
- The `translate-use-legacy.flag` escape hatch is gone from the scheduler and
  the admin panel
- An `ExecStart` pointing anywhere else is now **a fault to report**, not a
  supported mode: the scheduler restores it every five minutes and the admin
  panel shows a red *Program: WRONG* tile

`scripts/ops/translate-window-check.sh` is now **in the repo**. It had been
host-only while holding both the watchdog fix and the program guard; a rebuild
would have lost them silently.

## 5. Admin panel — schedule and audio from the browser

`/admin` can now edit both without SSH.

- **Schedule** → `config/schedule.conf`, one directive per line so both the
  shell script and Python parse it. The scheduler falls back to built-in
  windows if the file is missing. `drain_min` is read in **its own pass** —
  reading it alongside the windows applied a stale value to any window above it.
- **Audio** → `config/settings.yaml`: input device, and per language the output
  device, channel and enabled flag.

Rejected before writing: days outside 1–7, non-`HH:MM` times, an end before its
start, windows overlapping on the same day, drain outside 0–180, and **two
enabled languages claiming the same device and channel** (they would talk over
each other; "Both" conflicts with Left or Right). Writes are atomic and keep a
`.bak`.

A device already open by translation **vanishes from enumeration** — the
Behringer does this during a service — so the picker keeps the configured name
marked *"in use / not detected"* rather than silently offering to change it.

Verified end to end: a schedule written through the API made the scheduler drain
the backlog and start translation.

## 6. Method notes — traps worth not repeating

- **Log replay cannot validate flush changes.** loguru timestamps have second
  resolution, so the sub-second gaps driving the silence timeout are
  unrecoverable. A replay of one service showed 0.6% leading marks against
  production's 17.8%. Use `tests/capture_fragments.py`, which records real
  arrival times, then `tests/sweep_flush.py`.
- **The harness must mirror the coordinator.** `feed()` is called when a chunk
  produced text and it *returns*; `tick()` runs only on an empty chunk. The
  silence timeout is therefore quantised to whole chunks, so with 1.5 s chunks
  **1.0 s and 1.5 s are the same setting.** An earlier harness ticked every
  100 ms and manufactured a difference that does not exist.
- **LaBSE under-penalises the errors that matter.** A negation flip scores 0.76
  against 0.90 for a correct translation, comfortably inside "acceptable". Use
  it to *rank* candidates, then read them. Its absolute scores are optimistic,
  and it rates Creole higher than reading suggests.
- **`pkill -f` / `pgrep -f` match the invoking command line.** This killed the
  SSH session and, once, a freshly started capture. Use PIDs, or verify
  `/proc/PID/comm`.
- **`print()` to a redirected log is block-buffered.** Startup lines can lag
  minutes. Verify configuration from `/proc/<pid>/environ`, not the log.
